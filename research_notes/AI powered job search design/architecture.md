# AI and manual job search architecture

Research date: November 1, 2026. Scope: technology jobs worldwide; AI is a core search interface alongside fully capable manual search; no map in this release; modular future features. This is a proposal, with no application changes made during this research.

## What can we reuse and what currently limits the module?

### Takeaway
Reuse provider adapters, shared AI model construction, job details, bookmarks, provider budgets/leases, and source verification. Rebuild the search boundary around a validated shared intent and bounded requested result pages; do not rewrite the resume editor or deploy a separate jobs service yet.

### Cited Findings
- `JobService.Search` queues external JSearch work, calls `repo.List`, builds a list of allowed sources, then invokes `jobmap.FilterJobs` on the returned in-memory slice. It shortens descriptions only after this filtering. This is implementation evidence, not a claim that the current traffic has already overwhelmed the server. — [Current job service](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/service/job_service.go)
- `JobRepository.List` selects every listing satisfying availability and saved-state conditions and unmarshals each JSON payload. Its search path has no SQL `LIMIT` or keyword/country filtering. Normal unsaved browsing uses a 72-hour freshness window; `Prune` removes unsaved listings whose latest fetch/check is older than 14 days. Bookmarked stale records are retained. — [Current job repository](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/repository/job_repo.go)
- `FilterJobs` requires every query word to occur in title/company/description, does filters, sorts, deduplicates identical canonical application URLs, and only then slices local pages. An empty remote country matches all remote policies, independently of map viewport/country. — [Search implementation](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/jobmap/search.go), [RemoteMatches](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/jobmap/places.go)
- Startup now schedules employer-feed refresh only and logs `himalayas_feed_enabled=false`; the full Himalayas function still exists but is not scheduled. Source status returned through the service overrides Himalayas' durable state to `paused`. Individual Himalayas availability checks remain in `Get`. — [Worker](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/service/job_workers.go), [Service](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/service/job_service.go), [Verification](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/service/himalayas_service.go)
- JSearch currently requests `num_pages=1`; its background import uses a database lease/cache and request budget, survives browser cancellation, and is bounded by a work timeout. It stores jobs globally; it does not retain a paged ordered membership list for each search. — [JSearch request](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/jobmap/providers.go), [JSearch worker](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/service/jsearch_service.go)
- Existing search builds supplemental provider queries only when a usable country or bounded map area is available; an unscoped remote query returns no JSearch query rather than silently searching a default US inventory. Removing the map therefore requires replacing this query construction, not merely hiding its React component. — [ExternalSearch](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/jobmap/search.go)
- `internal/ai.NewChatModel` returns an Eino `ToolCallingChatModel`, supports configured Anthropic/OpenRouter, and centralizes provider options. `internal/agent` already constructs `adk.ChatModelAgent`, `adk.Runner`, explicit tools with parameter schemas, request session values, and streamed tool/text events. Eino is pinned to v0.9.12. — [AI model](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/ai/client.go), [Agent](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/agent/agent.go), [Chat/tools](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/agent/chat.go), [Go dependencies](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/go.mod)
- The current resume assistant explicitly limits itself to editing a specific resume; its tool set contains resume edits, template/layout actions and draft reads. It does not provide job search. — [Current assistant scope and tool list](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/agent/chat.go)

### Inferences
- Proposed responsibility split: provider-neutral `jobs` domain/search orchestration, current repository/service layers, plus a small in-process `jobagent` package for natural language and explanations. Reuse `internal/ai` rather than add another model client. Keep the resume assistant's mutation tools out of the job search assistant; a later explicit “Tailor my resume for this job” action can hand selected job context to it. This avoids making ordinary job search capable of editing a resume.
- Keep strict layering: HTTP adapter -> job application service -> repository. Provider network adapters remain a dependency of the job service, not an HTTP handler. AI tools are another adapter calling those same services; they never call SQL or provider URLs chosen by the model directly.
- Start with the current Go process, Postgres and React. Separate packages/interfaces provide useful modularity now. A new microservice, vector database, multi-agent search fleet, geocoding stack, or mandatory queue is not required by the user's stated scope.
- Worldwide tech coverage needs a deliberate capability model. The current English tech-title regex can admit adjacent roles and miss non-English titles. Retain the source title/language/category and treat uncertain “tech job” classification explicitly; do not promise multilingual matching because the application serves international countries. — Design implication of [Current normalization](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/jobmap/normalize.go)

### Gaps
- No load test or profiler evidence establishes a capacity threshold, memory cost per listing, current database pressure, or LLM dollar cost. Do not write that 15,000 records by itself will “choke” this server. The verified issue is work per search grows with the cached inventory.
- Actual multi-country coverage/recall must be measured with provider test searches. API availability does not prove broad country coverage or consistent filtering.

## How should AI and manual search share one engine?

### Takeaway
AI should turn conversation into inspectable structured search criteria, call the same search service manual filters call, and explain returned records with evidence. It must not invent jobs, silently relax hard preferences, or convert an attractive fit score into eligibility.

### Cited Findings
- Eino separates tool selection from execution: the chat model produces tool calls and `ToolsNode` executes configured tools. Tool parameter schemas, argument handlers, execution policy and middleware are available. This provides a compatible foundation for a narrow typed job-search tool. — [Eino ToolsNode guide](https://www.cloudwego.io/docs/eino/core_modules/components/tools_node_guide/)
- Eino's official architecture discussion distinguishes open-ended conversational agents from predefined workflows, and recommends exposing deterministic workflows as tools to an agent. — [Agent or Graph](https://www.cloudwego.io/docs/eino/overview/graph_or_agent/)
- The existing job model distinguishes office locations and remote policy, but salary is currently a display string. It lacks first-class structured salary range/currency/period, visa sponsorship status, requirement evidence and language fields. Existing employment normalization folds several categories into a smaller enum. — [Current job model](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/jobmap/types.go), [Normalization](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/jobmap/normalize.go)
- Himalayas documents salaries as amounts in a stated pay period and currency; country restrictions and timezone restrictions are separate concepts. Its dictionary also states that a missing salary is null, not zero. Some current public field examples differ from this repository's country-string/numeric-offset decoder; integration tests should verify actual endpoint responses rather than assume a schema matches. The provider researcher verified a live India software-engineer search response using country strings and numeric offsets, matching the current decoder; the disagreement is documentation versus observed endpoint output, not evidence that today's adapter is broken. — [Himalayas data dictionary](https://himalayas.app/docs/data-dictionary), [Live search endpoint checked by provider researcher](https://himalayas.app/jobs/api/search?country=IN&q=software%20engineer&page=1), [Current decoder](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/jobmap/himalayas.go)

### Inferences
- Proposed shared `SearchIntent`: role/keywords; required and preferred skills; arrangements (remote/onsite/hybrid); office city/country choices; remote candidate country and timezone; employment type; seniority; salary minimum + ISO currency + pay period; posted/updated date preference; include-unknown flags; exclusions; sort; selected resume version (optional); language preference (future-compatible). Do not present every field at once. Treat only user-relevant controls as primary.
- Each interpreted constraint should carry provenance: explicitly stated by user, set by manual control, or suggested from a selected resume. Inferred criteria appear as editable chips. The same visible intent governs both chat refinements and filter changes; changing a manual filter must update the assistant's context, not leave two competing states.
- Example: “Find backend Go jobs, remote from Germany or hybrid in Berlin, mid level, ideally EUR 70k+ annually.” Normalize to two explicit arrangement/location branches. If salary is “ideally,” rank it softly; if “only EUR 70k+ with disclosed salary,” make it hard and show the expected unknown-salary exclusion. Do not turn an OR across remote/hybrid into an accidental AND.
- Pipeline: conversation/manual controls -> schema-validated intent -> provider capability-aware query plan -> bounded fetch/cache -> canonical normalization -> deterministic eligibility filtering -> ranking -> result cards and evidence-grounded AI summary. This pipeline can be ordinary Go services; Eino graphs are optional orchestration, not a reason to rewrite deterministic logic as a model loop.
- Hard constraints: explicit candidate-country restrictions, required attendance location, selected arrangement, explicit exclusion/mandatory preferences, expiration/closure. Unknown country/visa/attendance/salary stays unknown. Eligibility evaluation should return `match`, `no_match`, or `unknown` plus reason and source. Hide explicit mismatches by default; user controls whether unknowns are included. Never infer visa sponsorship from “remote,” company nationality, or worldwide hiring.
- Soft ranking: role/title relevance, observed skills, stated experience compatibility, salary preferences, recency and optional user feedback. A skill absent from a resume is “not evidenced,” not a fact that the candidate cannot do it. A requirement absent from a job description is unknown, not waived. Display short explanations with source snippets (“Go listed in your project; role requests Go”), not a hiring-probability percentage.
- Initial AI capabilities: parse/refine criteria, run search, explain fit of returned job IDs, compare a small shortlist, save/hide a selected result after an explicit user action, and hand off a job to resume tailoring. Keep direct apply as a visible source-link action. Automatic applications, recruiter outreach, silent resume edits, invented requirements and unsupported visa claims are outside MVP.
- Do not ask every user to complete a full profile before their first search. Ask a focused question when it changes correctness (e.g. remote work country), otherwise show editable assumptions and allow manual browsing immediately.
- Manual search should run without an LLM call. AI input parsing and optional fit explanations can fail or be rate limited independently; typed controls and existing results remain usable.
- A selected resume is a per-search private context. Let users search without one. For resume-aware matching, let them choose the resume and whether to use the current local draft or saved version; label the snapshot/version so rankings are reproducible and unsynced edits are not silently ignored.

### Gaps
- No defined relevance benchmark, ranking weights, supported languages, international salary conversion policy, or sponsorship source coverage exists yet. These need explicit product decisions and measurements, not arbitrary model-generated numbers.
- It is not established that each provider can honor every intent field. Unsupported hard constraints must be applied after normalization or reported as unknown; the UI cannot pretend an unsupported upstream filter was enforced.

## How can requested pages stay bounded and counts remain honest?

### Takeaway
Cache requested search pages, ordered result membership and canonical jobs, with explicit eviction and provider budgets. Distinguish results actually fetched from provider estimates; an on-demand federated search does not justify an exact global result count or a globally sorted inventory claim.

### Cited Findings
- PostgreSQL supports JSONB indexing and recommends predictable JSON structures; documents and relational columns can coexist. This gives a path to index stable filter fields without adding a search platform immediately. — [PostgreSQL JSON types](https://www.postgresql.org/docs/current/datatype-json.html)
- PostgreSQL documents that paginated queries require a unique predictable order and that large OFFSETs still compute skipped rows. — [PostgreSQL LIMIT/OFFSET](https://www.postgresql.org/docs/current/queries-limit.html)
- Current cross-source deduplication only groups identical normalized application URLs, preferring a saved record. It deliberately does not collapse company+title, which could merge distinct vacancies. — [Current FilterJobs/ApplicationKey](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/jobmap/search.go)
- The existing repository already has source-job IDs, upserted JSON payloads, separate bookmarks, availability state, request reservations, cache/lease methods and cleanup. These are useful building blocks rather than throwaway code. — [Current repository](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/repository/job_repo.go)

### Inferences
- Proposed persistent concepts: canonical jobs; provider references for each canonical job; normalized public search keys; cached provider pages and result-ID order; short-lived search sessions carrying cursors; existing user bookmarks; optional private user search context and selected-resume match assessments. Start with the minimum tables required, not a full event platform.
- Public cache key must include provider, supported filter representation, country/eligibility intent, requested page or cursor, sort and adapter/schema version. Resume identifiers, identity, private exclusions and personalized scores must not be shared in that cache. Cache generic provider results once, apply private ranking/preferences separately.
- Fetch page one for relevant providers with bounded concurrency. Fetch additional provider pages only when a user selects load more or when a small bounded refill is needed after deterministic filtering/dedup. A sparse first page is not permission to crawl every page. Set per-search max pages, max expanded queries, max provider calls, execution deadline, and a separate global provider allowance, all enforced in code rather than in a prompt.
- Database-backed request coalescing/leases should prevent many users asking the same question from generating duplicate upstream calls. Use a cache freshness TTL chosen per source and its terms, plus hard maximum cached rows/bytes or eviction threshold; TTL alone does not bound storage if distinct searches arrive faster than expiration. Saved jobs can be retained separately with clear closed/stale states.
- Move locally cached job filters and pagination into repository SQL using indexed stable fields. Keep raw source payload for traceability. Project only list fields on search; obtain full descriptions for detail/AI fit analysis when needed. Measure query plans before selecting indexes; JSONB is an option, not an automatic speed guarantee.
- Keep initial result ordering stable within a search session, and carry opaque per-provider cursors/next-page tokens plus emitted canonical IDs for dedup. Load-more should append; a fresh search may rerank. Do not reshuffle already visible cards every time another provider finishes.
- Offer “N jobs loaded” with per-source freshness/completeness, and `hasMore`/load-more. A provider's approximate total is a source estimate, not our exact distinct count. Across overlapping providers do not sum totals. Sorting by salary/recency across fetched results should be labeled accordingly unless a full inventory is actually available.
- Preserve exact identity by provider+provider ID. Cross-provider grouping can use a reliable canonical application or employer requisition reference when available; keep alternative sources and apply links. Fuzzy title/company matches can be candidate duplicate groups but must not silently merge remote/onsite openings or separate requisitions.
- Handle a provider timeout, exhausted quota, empty response, stale cache, and schema error separately. Return results from healthy sources with “partial results/source unavailable”; never report an outage as “no jobs exist.” Respect Retry-After and use bounded retry/backoff. Existing good per-provider interruption/bookmark-preservation behavior can be reused.
- Cancelling a browser interaction may leave a short, bounded generic cache fill running when it benefits other users; do not run unbounded personalized agent work after cancellation. Manual filtering cached pages should not make new model calls.

### Gaps
- We have not measured expected traffic, cache hit rate, provider latency, cache working-set size or current query plans. Choose numerical caps/TTLs as explicit initial operating budgets and tune with observations; do not publish invented capacity or cost estimates.
- The provider-research notes own verified endpoint limits and retention rules. This architecture must respect those per-provider constraints, including source attribution and expiry behavior; generic caching advice cannot override a provider contract.

## How should authorization, AI trust boundaries, and rollout be handled?

### Takeaway
Keep user identity and authorization in deterministic services, expose narrow tools, and treat job descriptions and resumes as untrusted content. Build a measured manual search foundation and a typed AI entry point together, then add evidence-based personalization without giving the search assistant unrelated powers.

### Cited Findings
- Resume ownership is enforced by `ensureResumeOwner`, reached through `ResumeService.Get` and `GetFullResume`. The current HTTP agent adapter verifies access through `ResumeService.Get` before sending the selected draft to the assistant. A new AI adapter should use the same services rather than bypass ownership in repositories. — [Ownership helper](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/service/ownership.go), [Resume service](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/service/resume_service.go), [Agent adapter](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/api/handlers/agent_handler.go)
- OWASP identifies indirect prompt injection from retrieved websites/files, including malicious job-description instructions. It recommends deterministic format validation, least privilege, clearly separated external content, and adversarial testing; RAG alone is not a complete mitigation. — [OWASP prompt injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
- OWASP excessive-agency guidance recommends narrow tools, user-context execution, downstream authorization and approval for high-impact actions rather than trusting model judgment. — [OWASP excessive agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- The current Himalayas detail flow treats provider failure as unconfirmed availability and preserves bookmarks, uses cached recent checks, and marks closures only on a confirmed closure response. — [Current verification](C:/Users/adity/OneDrive/Desktop/resume-builder/backend/internal/service/himalayas_service.go)

### Inferences
- Job AI session identity comes from authenticated request context, never model-supplied user ID. Read a selected resume through `ResumeService`; no tool-level duplicated ownership rules. Saved searches/bookmarks and future applications likewise go through user-scoped service methods.
- Send generic role keywords, country and chosen public filters to job providers, not a raw resume or chat transcript. The AI model gets the minimum selected-resume content needed for the user's chosen task; redact contact information from skill matching. Make personalization opt-in for a selected resume, disclose use, and keep snapshots/scores private to the user. This is a privacy design proposal, not a legal-compliance claim.
- Tool allowlist for MVP: validate/refine intent, search jobs, get returned job detail, read selected resume summary, explain/compare returned job IDs, and explicit saved-job actions. Return structured real IDs and trusted links; render listings directly from those tool results. If the model emits a made-up ID or URL, reject it. No arbitrary URL-fetch, SQL, shell, email, auto-apply or general resume-mutation tool belongs in the search assistant.
- Treat source descriptions and resume fields as data even when they contain tool instructions. Sanitize rendered HTML, retain provenance and cap text length. A prompt sentence saying “ignore malicious instructions” is one layer, not the security boundary; only deterministic services authorize effects.
- Ship sequence: (1) define intent/job/provider contracts and fixtures; remove map dependencies from search construction; supply working manual location/remote controls and bounded provider pages; (2) add natural-language -> shared intent + tool search with visible criteria and follow-up refinement; (3) optional resume snapshot, evidence-linked match explanations, shortlist comparisons, explicit tailoring handoff; (4) alerts, application tracking and advanced multilingual/semantic search only when user demand and data quality justify them. Avoid making AI a cosmetic later add-on: phase 1 contracts and phase 2 interaction should be one planned first release.
- Validation should cover intent equivalence (same manual filters vs natural language), negation/OR branches, no silent broadening, remote-country/timezone constraints, unknown visas/salaries, salary period/currency, pagination after dedup, cache isolation, cancellation/shutdown, provider quota/outage/429/invalid-schema paths, source attribution and expired jobs. Add prompt-injection fixtures and invalid-job-ID output checks. Use small curated realistic queries across several countries rather than a model judging its own answers without evidence.
- Product quality metrics: explicit eligibility violations, duplicate rate, stale/closed-result rate, supported-intent extraction accuracy, user correction rate, saves/relevant opens per search, manual fallback success, source coverage and failure rate. Operating metrics: provider calls per search/page, cache hit rate/bytes, LLM tokens and tool calls, latency split by parsing/provider/ranking. Counts require observed measurements; no target percentages are asserted here.
- Modular future expansion: version SearchIntent and normalized Job; expose per-provider capabilities; isolate optional ranking/explanation plugins; preserve source text/language and provenance; keep AI context separate from public cache; leave office coordinates optional so a map can be added later without making it the search model again.
- Future modules should attach via stable job and user identities: saved searches reference versioned intent, recommendations store preference/evidence versions, applications reference a canonical job plus private stage/history, alerts consume saved intents with their own operating budget, and maps read optional office coordinates. Do not build these modules into the first search release merely to prove the interface can support them; preserve the keys, service boundaries and optional fields now.

### Gaps
- User data retention duration, deployment privacy requirements, model-provider data handling settings, traffic budget and target countries/languages still require product decisions. Do not invent legal requirements or prescribe a paid plan from these notes.
- A “match” explanation is informational search help, not a verified assessment of employer hiring decisions, immigration eligibility or probability of employment.
